# bring-up 明账 —— 「跑通了」覆盖了什么,没覆盖什么

**这张表存在的唯一理由**:第一次整网跑通时,「跑通」会被读成「验过」。
**它们差得很远**,而差在哪里只有当场写下来才留得住。

每行三列:**✅ 这次真的验了什么 / ❌ 没验什么 / ⚠️ 为什么「跑通」不构成验过**。

> 🔴 **出处标注是这张表的一部分。** 下面很多证据不是我测的 ——
> 把别人的实测写成自己的,会让这张表在被追问时崩掉一格,而那一格会带走整张表的可信度。
> 每行末尾的 `[来源]` 就是这个用途:`[golden 实测]` 是我跑的,其余是转述,**未经我复核**。

## 一、协调方点名的六条

### 1. bf16 KV —— 量化路径零覆盖

| | |
|---|---|
| ✅ | 584 B 的格式与 CANN `quant_mode=2` **逐字节相同** `[kernel 实测,未经我复核]` |
| ❌ | **量化路径本身一次都没跑过。** 第二步只是 dispatch `[kernel 报告]` |
| ⚠️ | 「格式对得上」和「量化算得对」是两件事。**格式相同只说明两边在读同一种字节布局**,不说明写进去的数对。一个把 scale 算错但格式正确的实现,过得了字节比对,过不了数值比对 —— **而数值比对还没跑** |

### 2. 两级候选筛 —— ≤16K 精确 no-op

| | |
|---|---|
| ✅ | 6 组性质在**真参数**下通过(`candidate_topk_blocks=2048` × `candidate_block_size=8`),`test_candidate_filter.py` `[golden 实测]` |
| ❌ | **筛子在整网里有没有被正确接上**,完全没验 |
| ⚠️ | 🔴 **筛子只在 > 16384 个位置时生效**(2048 块 × 8)⇒ **≤16K 的 GSM8K 碰不到它一次**。一个筛子**完全没有实现**的版本,在 16K 以内会给出和正确实现**完全相同**的结果。<br>⇒ 我那 6 组性质里**有 4 组在 ≤16384 下是空的**,其中第 3 条最要紧:**最新位置所在的块被 `+inf` 钉住**,否则一个更老的满块会把它挤掉、**最近的 token 就丢了**。NPU 漏实现它在短上下文下没有任何症状 `[golden 实测]` |

### 3. `ratio=2` 的数值正确性 —— 只到 `executes`

| | |
|---|---|
| ✅ | `cmp_ratio=1` 正确,max rel err 2.961e-03 `[kernel 实测]`;`ratio=2` 算子接受并跑出**有限**输出 `[kernel 实测]` |
| ❌ | **`ratio=2` 一个数值判据都没有** |
| ⚠️ | 「有限的、形状正确的输出」离「对的输出」很远。实测:把两条流的合并猜成「各自 softmax 再合」,得到的答案**也是有限的、形状也正确的**,只是差 **6.5e-01** `[kernel 实测]`。<br>⇒ 两流参考已写好(12 用例全过,`[kernel 实测]`),数值定义来自 `TWO_STREAM_ATTENTION.md` `[golden 出品]`,**但两边还没对上过** |

### 4. DSpark / MTP drafter —— 一行未动

| | |
|---|---|
| ✅ | 无 |
| ❌ | **全部**。官方实现显式 `raise`,无可抄 `[协调方报告]` |
| ⚠️ | 这条不是「验得不够」,是**根本没做**。估 8~12 人天 `[协调方估计,未经我复核]`。**「跑通」的那条路径不经过它** |

### 5. engram host 路径吞吐 —— 从没测过

| | |
|---|---|
| ✅ | 查表的**数值**参考就绪并自验通过(`engram_lookup_ref.py --verify`,7 个 key)`[golden 实测]`;`ElasticBuffer` 的 engram 路径**字节透明**(埋 2080 个 NaN + 16 个 Inf 全部逐位存活)`[golden 实测]` |
| ❌ | **吞吐一次都没测过** —— 189.1 GiB 表放 host、按需取行,**每 token 要取 2×24 行** |
| ⚠️ | 数值对不代表跑得动。**这条是性能风险,不是精度风险**,所以它不会表现为「结果错」,会表现为「慢得不能用」—— 而精度门禁一个都不会响 |

### 6. 🔴 `sparse_flash_mla` 的 BF16 plan —— 我们之前从没被端到端跑过

| | |
|---|---|
| ✅ | 无(在我们之前:代码里存在,**零测试零日志**)`[协调方报告]` |
| ❌ | 这条 plan 的**一切** |
| ⚠️ | 🔴 **「跑通了」本身就是这条 plan 的首次验证,而它同时是被测对象和测试环境。**<br>⇒ 这一格的性质和其他五格不同:其他五格是「某个东西没验」,**这一格是「用来验别人的那个东西自己也没验过」** ⇒ 它上面跑出来的任何结论都要打一个折,而且**这个折没法从结论本身看出来** |

## 二、golden 线补充的五条(协调方没列,但同属「跑通 ≠ 验过」)

### 7. NPU 侧的 decode 路径 —— CPU 上验过,NPU 上没有

| | |
|---|---|
| ✅ | prefill↔decode 自洽(判据 G-1)在 **CPU golden** 上双模式通过;环形缓冲回绕通过 `[golden 实测]` |
| ❌ | **NPU 的 decode 路径没有任何逐层对照** |
| ⚠️ | decode 会碰到 prefill 完全不碰的东西:环形缓冲的写位置、`start_pos` 寻址、`indexer_kv_offset` **从 `seqlen` 变成 `window_size`**(实测 prefill 时 = 27)。**跑通 prefill 对这些一个都没覆盖**(协议 §11.1) |

### 8. `batch > 1` —— 是诊断,不是门禁

| | |
|---|---|
| ✅ | 定性完成:第一处分歧是 layer 0 的 `hc_mixes.0.0` 差 **3.638e-12**(fp32 舍入量级),强制路由只减 4.4× `[golden 实测]` |
| ❌ | **并发下的数值正确性没有门禁** |
| ⚠️ | 🔴 **两行不可能逐位相同,那个目标不可达**。所以 `compare_batch_rows.py` 判的是**第一处分歧的形状**(阈值 1e-6),**它是诊断工具,不能拦发布**。<br>⇒ 而 **GSM8K 那一轮必然是并发的** ⇒ 并发路径的唯一门禁就是 GSM8K 的最终分数,中间没有任何拦截点(协议 §8.1) |

### 9. indexer 的 100% 稳定 —— 只在 K=13 的条件下成立

| | |
|---|---|
| ✅ | fp32↔fp64 扰动下 `indexer_topk.out` **100% 一致** `[golden 实测]` |
| ❌ | **长序列下没测过** |
| ⚠️ | 实测 `K = min(index_topk=512, end_pos//ratio)`,27 token 在 ratio=2 的层上 **K=13,是「13 个里选 13 个」—— 没有选择余地**。<br>🔴 **T=1100 已补测(K=512 / 候选 550,有选择余地),两个结论**:<br>**(a) 判据站得住**:合法的更准扰动(fp32→fp64)在**隔离模式**下让 `indexer_topk.out` 差 **0/1100 = 0.00%** ⇒ **「逐位相同」这条要求在它该用的模式里成立,长序列也成立。**<br>**(b) 但自由累积模式下差 64/1100 = 5.82%** ⇒ 那是输入已经分叉的后果,不是 indexer 自己不稳(第 0.1 节已说明自由累积下逐层比对无意义)。<br>⇒ **indexer 的选择在输入相同时是稳定的,它只在输入已分叉后才翻。**<br>另:一个真实的语义错误(indexer 看 post-RoPE latent)让 6.8% 的行选出不同集合,而 `layer.out` 只差 7.408e-03 **低于阈值** ⇒ 判据必须落在选择上(协议 §5.3)`[golden 实测]` |

### 10. 中间部分和不能舍到残差 dtype —— 要求成立,但**要求的对象先前指错了**

| | |
|---|---|
| ✅ | EP=3 **和** EP=4 实测:同一批贡献在 **fp32** 里以任意顺序/分组求和,`moe.out` 上是 **0.000e+00,40 层每层都是 0**。**这条与数据流无关** ⇒ 「我们分片、golden 不分片」不能解释 `moe.out` 的任何不一致 `[golden 实测]` |
| ✅ | **本部署下 MoE 那条 `all_reduce` 是 no-op**:TP 组 `world_size == 1`(A5 硬约束),`vllm/distributed/parallel_state.py:737-739` 原样返回输入 ⇒ `fused_moe.py` 的 200/241/259 三处一个字节都不动;昇腾在自己的 dispatch/combine 里归约(`fused_moe.py:245` 注释)`[golden 自核,integration 首先指出]` |
| ❌ | **`npu_moe_distribute_combine_v2` 内部的累加精度,没人测过** |
| ❌ | **`moe.out` 在 NPU 上的误差由哪个算子产生,未定位** |
| ⚠️ | 🔴 **我先前把这条写成「`all_reduce` 必须在 fp32」,并在消息里说过「现在知道 NPU 侧确实走的就是 bf16 那条路」—— 后半句是错的,已撤回。** 我把一个「`dist.all_reduce` 在 bf16 张量上按 bf16 累加」的测量,顺着滑成了「`moe.out` 的误差来自它」;**那是两个主张**,第二个需要「那条路径在本配置下存在」,而它不成立。 |
| ⚠️ | 那个 **5.00e-01** 仍然是一个真实的代价,但它模拟的是**一种实现选择**(把每组部分和先舍到残差 dtype),**不是 NPU 的已测属性**。⇒ **先定位算子,再谈改。** 顺序反了会改错东西,而改错东西之后「没变好」会被当成「这条结论错了」 |

### 11. fp4 的两个问题 —— 必须有 GPU 才能定

| | |
|---|---|
| ✅ | CPU 侧的 fp4 nibble 打包顺序与 `convert.py` **逐字一致** `[golden 实测]` |
| ❌ | **e2m1 的舍入模式**(若不是 RNE,中点元素最大偏差 **33%**);**nibble 打包顺序的另一侧** |
| ⚠️ | 这两条**无法在没有 GPU 的机器上判定** —— 不是「还没做」,是「这台机器上做不了」。风险低但若打包顺序反了是灾难性的(协议 §10.6) |

## 三、怎么用这张表

1. **第一次跑通时和结果一起发**,不要晚发 —— 晚一天,「跑通」就已经被当成「验过」传出去了。
2. **每一行的 ⚠️ 列是给读结论的人看的**,不是给做事的人看的。做事的人知道自己没做什么;**读结论的人不知道**。
3. **第 6 条要单独提**。其他十条是「某个东西没验」,第 6 条是「**用来验别人的那个东西自己没验过**」——
   它会给所有在它上面得到的结论打一个折,而**这个折没法从结论本身看出来**。
4. 🔴 **不要用这张表去反对上线。** 它的用途是**让「跑通」被正确解读**,
   而不是主张「没全验完就不能跑」。把风险摆清楚之后,要不要接受是别人的决定。
